# steam-recommend 추천 엔진 설계

플레이 여부(binary)만 쓰는 단순 추천이 아니라, **플레이타임·태그·리뷰·동시보유(co-play)** 신호를
통계적으로 결합하는 하이브리드 추천 시스템. 모든 계산은 서버에서 실시간으로 수행하되,
사용자 독립적인 데이터(게임별 태그/리뷰/동시보유 분포)는 공격적으로 캐시한다.

## 데이터 소스

| 소스 | 엔드포인트 | 용도 | 캐시 |
| --- | --- | --- | --- |
| Steam Web API | `IPlayerService/GetOwnedGames` | 라이브러리 + 플레이타임 + 최근 플레이 시각 | 없음 (개인화) |
| Steam Web API | `ISteamUser/GetPlayerSummaries`, `ResolveVanityURL` | 프로필, 커스텀 URL 해석 | 없음 |
| Steam Store API | `api/appdetails` | 장르, 출시일, 이미지, 설명, 가격 | 24h (appid별) |
| Steam Store API | `api/featuredcategories` | 신작/인기/할인 후보 풀 | 1h |
| Steam Store API | `appreviews/{appid}` | 리뷰 통계(최신) + 리뷰어 SteamID 표본 | 24h / 7d |
| SteamSpy | `api.php?request=appdetails` | **태그(투표수 포함)**, 소유자 추정, 중앙값 플레이타임 | 24h (appid별) |

Steam Web API 키는 서버 전용(`STEAM_API_KEY`). 브라우저에서 직접 호출하지 않는다.

## 1. 암묵적 선호 가중치 (implicit confidence)

Hu–Koren–Volinsky(2008)의 암묵적 피드백 신뢰도 아이디어를 단일 사용자 설정에 맞게 적용.
게임 `g`에 대한 선호 가중치:

```
engagement(g) = playtime(g) / median_playtime_global(g)   # SteamSpy median_forever로 정규화
w(g) = log2(1 + hours(g)) · min(2, 0.5 + engagement(g))   # 절대량 × 상대적 몰입도
w(g) *= recency_decay(last_played, half_life = 2y, floor = 0.35)
```

- `log` 감쇠: 플레이타임의 한계효용 체감 (Dota 3,000시간이 프로필을 지배하지 않도록)
- **중앙값 정규화**: 10시간짜리 게임을 30시간 한 것이 MMO 30시간보다 강한 신호
- 시간 감쇠: 취향 변화 반영 (반감기 2년, 하한 0.35 — 오래된 취향도 완전히 버리지 않음)

## 1.5 Spotify 공개 기법의 차용

Spotify가 논문·기술 블로그로 공개한 추천 기법 중 세 가지를 스팀 도메인에 맞게 적용했다:

| Spotify 기법 (공개 출처) | 우리 구현 |
| --- | --- |
| **Taste clusters** — 청취 이력을 하나의 평균이 아닌 여러 취향 클러스터로 표현 (Discover Weekly 해설) | 플레이한 게임의 태그 벡터를 가중 구형 k-means(K≤4, 결정적)로 클러스터링. 후보는 **최근접 클러스터**와의 코사인으로 평가(max-over-clusters) — 평균 벡터가 로그라이크+농장 시뮬 취향을 뭉개는 문제 해결 (`clusters.ts`) |
| **암묵적 피드백 신뢰도** — 재생 횟수 기반 confidence 가중 (Hu–Koren–Volinsky ALS 계열) | 플레이타임 log 감쇠 × 중앙값 정규화 × 시간 감쇠 선호 가중치 (§1, 기존) |
| **explore/exploit의 아이디어** — 대부분은 아는 취향을 활용하되 일부 슬롯은 탐험에 배정 (BaRT; McInerney et al., RecSys 2018 "Explore, Exploit, and Explain") | 숨은 보석 마지막 슬롯 = **탐험 픽**: 점수 순위 밖이지만 품질 검증(WLB≥0.75)된 최고 novelty 후보를 **결정적으로** 발탁 (`rankHiddenGems`). ⚠️ 노출·보상·반응 로그가 없으므로 bandit/ε-greedy가 **아니다** — 아이디어만 차용한 결정적 규칙 (원장 C12) |

또한 Spotify가 유저 행동 특성(청취 시간대·다양성 등)을 별도 신호로 쓰는 것에 대응해,
**플레이 성향(persona) 프로파일**을 도입했다 (§2.5).

## 2. 취향 벡터 — 태그 TF-IDF + 코사인 유사도

- 게임의 태그 벡터: SteamSpy 태그 투표수를 `sqrt` 감쇠 후 L1 정규화 → TF
- IDF: 사용자 라이브러리 작업 집합 내 문서빈도로 `log((N+1)/(df+1))+1`
  — "Action", "Indie" 같은 만능 태그의 지배를 억제. 취향 프로필이 라이브러리 태그
  공간에 놓이므로 IDF도 같은 공간에서 산출하고, 후보의 미지 태그는 기본 IDF(=1)로 처리
- 사용자 프로필 벡터: `P = Σ w(g) · tfidf(g)` (플레이 ≥ 30분인 게임만; 미플레이 보유는 취향 증거가 아님)
- 후보 점수: `cosine(P, tfidf(c))`

## 2.5 플레이 성향(persona) 프로파일

태그 "내용"(무엇을 좋아하나)과 별개로, 플레이 "행동"(어떻게 즐기나)에서 성향 축을 추출한다:

| 축 | 계산 |
| --- | --- |
| 몰입(depth) | 플레이타임 HHI + 상위 5개 게임 비중 |
| 정주행(commitment) | (내 플레이 / 전체 유저 중앙값)의 중앙값, 로그 스케일 |
| 도전(challenge) | Difficult/Souls-like 등 고난도 태그의 가중 투표 비중 |
| 소셜(social) | 멀티 태그 vs 싱글 태그 비율 (가중) |
| 발굴(niche) | 플레이 게임의 소유자 수 로그 역스케일 (3만→1, 2천만→0) |
| 신작(fresh) | 플레이타임 가중 appid 백분위 (appid ≈ 출시 순서 근사) |

상위 특성 2개를 조합해 유형명("도전자 × 싱글 몰입러")을 부여하고 대시보드에 표시한다.
후보 게임과의 **성향 적합도(personaFit)** = 도전/소셜/니치 축 호환성(가중 1-|차|)으로,
태그 유사도와 독립적인 세 번째 랭킹 신호가 된다.

**가중치 재조정** — "태그 매칭이 너무 광범위하다"는 문제에 대응해 태그(취향) 항의
지배력을 낮췄다: 섹션 공통 `0.40·z(taste) + 0.35·z(WLB) + 0.25·z(fit)`
(기존 0.6/0.4에서 taste를 클러스터 매칭으로 바꾸며 비중 축소).
co-play는 `0.5·z(lift) + 0.2·z(taste) + 0.15·z(WLB) + 0.15·z(fit)`.

## 3. 품질 점수 — Wilson score 신뢰하한

리뷰 긍정 비율을 그대로 쓰면 표본이 작은 게임이 과대평가된다.
**Wilson score interval의 95% 신뢰하한**을 품질 점수로 사용:

```
WLB = (p̂ + z²/2n − z·√(p̂(1−p̂)/n + z²/4n²)) / (1 + z²/n),  z = 1.96
```

리뷰 10개에 100% 긍정(WLB ≈ 0.72)보다 리뷰 5,000개에 93% 긍정(WLB ≈ 0.92)이 위가 되는,
통계적으로 방어 가능한 순위. 숨은 보석 발굴에서 특히 중요하다.

## 4. 동시보유 신호 — "이 게임을 한 유저들이 많이 하는 게임"

아이템 기반 협업 필터링을 실시간 표본으로 수행:

1. 앵커 게임 선정: 사용자 `w(g)` 상위 K=3
2. 앵커의 리뷰 작성자 표본 M≈28명 수집 (`appreviews`, 공개 라이브러리 + 게임 5개 이상 보유자만)
3. 각 리뷰어의 공개 라이브러리를 조회해 게임별 동시보유 횟수 `n(Y)` 집계
4. 순위 통계량은 **smoothed lift (PMI)**:

```
lift(Y | A) = (n(Y) / M) / p(Y)        # p(Y) = SteamSpy 소유자 추정 중앙값 / 전체 모수
score = log( (n(Y) + s) / (M · p(Y) + s) )   # add-s 평활화, n(Y) ≥ 3 필수
```

원시 빈도 대신 lift를 쓰면 "모두가 가진 게임"(CS2, TF2)이 아니라
**앵커 플레이어 집단에서 기대치 대비 과대표된 게임**이 올라온다 — 이것이 진짜 연관 신호.
표본이 작으므로 평활화와 최소 지지도(n≥3)로 분산 폭주를 막는다.
앵커별 동시보유 분포는 사용자 독립적이므로 7일 캐시로 모든 사용자가 공유.

> **lift 해석의 한계(솔직한 명시).** ① 표본 M이 작아 기대치 `M·p(Y)`가 평활화 상수 `s`보다
> 작은 경우가 많아, 순위는 사실상 동반 플레이 빈도(coCount) 위주가 되고 인기도 보정은 완만하게만
> 작용한다. ② `p(Y)=owners/POP`의 `POP`(≈1.2억)는 프라이어이며, 평활화와 맞물려 순위에 영향을 준다
> (상수라 무영향이 아님). ③ 표본은 앵커의 최근 긍정 리뷰어 중 공개 라이브러리 사용자라 전체
> 모집단과 다르다. 따라서 UI의 "동반 ×N" 배지는 **근사치**로 표시하며, 이 섹션은 정밀한 통계적
> lift가 아니라 "같은 게임을 즐긴 사람들이 실제로 함께 하는, 전역 인기로 완만히 보정된 게임"으로
> 읽는 것이 정확하다.

## 5. 섹션별 랭킹

각 섹션 내에서 구성 점수를 z-정규화 후 가중합. 모든 카드에 근거 배지 표시
(매칭 태그, 리뷰 신뢰하한, lift 배수).

| 섹션 | 후보 | 점수 |
| --- | --- | --- |
| 백로그에서 추천 | 보유 & 플레이 < 2h | `0.6·z(cosine) + 0.4·z(WLB)` |
| 다시 잡을 게임 | 보유, 2h ≤ 플레이 ≤ 40h, 6개월+ 방치 | `0.65·z(cosine·(1−0.4·진행도)) + 0.35·z(WLB)` — 진행도 = 내 플레이/전체 중앙값 |
| 이 게임을 했다면 | 앵커별 co-play 상위 (미보유) | `0.55·z(lift) + 0.3·z(cosine) + 0.15·z(WLB)` |
| 신작 추천 | featured new_releases ∪ coming_soon (미보유) | `0.6·z(cosine) + 0.4·z(WLB)` — 풀 자체가 최신이라 별도 신선도 항 없음 |
| 숨은 보석 | co-play ∪ 신작·인기 후보 중 소유자 200만 미만, 리뷰 30+ (미보유) | `cosine^0.5 · WLB^0.3 · novelty^0.2`, novelty ∝ 1/log(owners) |

숨은 보석은 **인기도의 역수를 명시적으로 보상**해 유명하지 않지만 취향에 맞는 게임을 노출한다
(popularity-debiased ranking).

## 6. 취향 분석 대시보드

- TF-IDF 상위 태그 (기여 플레이타임 포함)
- 장르 분포 (플레이타임 가중)
- 통계 요약: 총/중앙값 플레이타임, 미플레이 비율, 플레이타임 집중도(HHI, Herfindahl 지수)

## 지연·비용 통제

- appid별 데이터는 `"use cache"` + `cacheLife`로 서버 캐시 (SteamSpy/appdetails 24h)
- SteamSpy·상점은 동시성 제한(≤6) + 전역 최소 간격 스로틀로 예의 있게 호출, 분석 대상 캡:
  취향 프로필은 플레이 상위 40개, 백로그 후보는 최대 100개, co-play 후보는 앵커당 25개
- 대시보드는 섹션별 `<Suspense>` 스트리밍 — 프로필 헤더 즉시, 무거운 섹션은 준비되는 대로
- 실패 격리: SteamSpy 다운 시 appdetails 장르를 균등가중 의사-태그로 폴백

## 알려진 제약

- `GetOwnedGames`는 대상 프로필의 게임 상세가 공개일 때만 응답 (비공개 → 안내 UI)
- 동시보유 표본은 리뷰 작성자 편향이 있음 (리뷰를 쓰는 유저 ≠ 전체 유저) — lift 통계와
  최소 지지도로 완화하되, UI에 표본 크기를 명시
- SteamSpy 소유자 수치는 구간 추정치의 중앙값 사용
